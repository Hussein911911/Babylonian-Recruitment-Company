## ٣) خمسة اكتشافات تُصحّح ما قبلها

### ١) تنزيل Storage من داخل الدالة يعمل على مشروع حقيقي ✔
البند الذي كان «محاكى» في الاختبارات صار مُثبتاً: الدالة قرأت الوعاء، اكتشفت
الملف `.sql` الوحيد، نزّلته، وحسبت بصمته. الردّ `READY` حمل `bytes` و`sha256`
و`statements: 403` قبل أي كتابة.

### ٢) `recreate-cron.sql` **غير لازم** بعد استرجاع الملف الكامل
المهام الأربع تُنشأ داخل الملف نفسه. المُقاس بعد الاسترجاع:

```
brc-auto-release   :: * * * * *      recovery-auto-backup :: 0 20 * * 5
recovery-ensure-fresh :: 10 1 * * *  hrc-card-archive-daily :: 15 0 * * *
```

### ٣) الإنتاج **لا يحوي** جدول `brc.app_secrets`
محاولة `select … from brc.app_secrets` على الإنتاج ترجع `42P01` — أي أن الإنتاج
يستعمل المصدر الأول (`current_setting('app.brc_secret')`) لا الجدول. والنتيجة
العملياتية: ملف النسخة **لا يحمل المفتاح** (مقصود)، والمشروع الجديد يبقى ناقصاً
حتى يُدخَل يدوياً. تحقّقنا في المشروع الجديد أن هذا هو **العائق الوحيد**:

```
select brc.verify_token('HRC-BC-000001');
→ ERROR 22023: مفتاح البصمة غير مضبوط أو أقصر من 16 حرفاً
```

### ٤) `form_serial_seq` غير مستعمل — فلا خطر تصادم
تعريفه ومنحه في المخطط، لكن لا دالة تنادي `nextval` عليه (أرقام البطاقات صارت
أبجدية-رقمية عشوائية). و`job_code_seq` آمن أصلاً لأن مولّد الكود يتخطّى المأخوذ:

```sql
loop v := 'HRC-' || nextval('brc.job_code_seq'); exit when not exists (select 1 from brc.jobs where code = v); end loop;
```

⇒ لا حاجة لـ`setval` لهما بعد الاسترجاع (خلافاً لما كان في `docs/SETUP-RUN-THIS.sql`).

### ٥) إعادة التنفيذ على قاعدة مسترجعة تفشل في المرحلة ١ — وهذا سلوك PostgreSQL
`create or replace view` لا يغيّر أعمدتها → `42P16 cannot drop columns from view`.
ولذلك صار في الدالة `reset=YES` (يمحو `brc` ويعيد بناءه). **ولا يُستخدم بعد نجاح
استرجاع** — إلا لتحديث نسخة قائمة بملف أحدث، أو لترميم محاولة انقطعت.

## ٤) ما أُضيف بعد الاسترجاع

- وعاء `job-images` (عام · حدّ ٢ م.ب · jpeg/png/webp) + سياستا القراءة العامة
  والكتابة للموظفين — **فارغ** (الصور خارج نطاق الحزمة بقرار المالك).
- الدالة `hrc-restore` ACTIVE · `verify_jwt: false` · والسرّ `RESTORE_TOKEN` مضبوط.

## ٥) المتبقّي — ولا شيء منه في القاعدة

| # | البند | لماذا لا يُنفَّذ آلياً |
|---|---|---|
| ١ | `brc` في **Exposed schemas** | إعداد منصّة (متغيّر بيئة PostgREST) لا SQL. لا يظهر في `pg_roles.rolconfig` ⇒ لا يُضبط بدور. **بلا هذا كل طلبات الموقع تفشل بـ`PGRST106`** — والموقع يستدعي `schema: 'brc'`. |
| ٢ | `brc_secret` | سرّ لا يُصدَّر في الملف، ولا يُرسل في محادثة |
| ٣ | الحسابات الثلاثة | تحتاج بُرداً وكلمات مرور؛ ثم يُربَط `brc.staff.auth_id` بـSQL |
| ٤ | `site_url` + `uri_allow_list` | ينتظران نطاق Cloudflare Pages الجديد |
| ٥ | الموقع نفسه | `npm run dist` يحتاج حاسوباً فيه Node |

قِيَم المصادقة الحالية في المشروع الجديد مطابقة للإنتاج (`jwt_exp=3600` ·
`disable_signup=false` · بريد مفعّل · هاتف معطّل · `mailer_autoconfirm=false` ·
`password_min_length=6` · `rate_limit_email_sent=2`) — فلا تغيير مطلوب الآن.

> ⚠️ `rate_limit_email_sent = 2` في الساعة: إن أُنشئت الحسابات من اللوحة
> (Authentication → Users → Add user) مع **Auto Confirm** فلا تُرسل رسائل،
> فلا تصطدم بالحدّ.
