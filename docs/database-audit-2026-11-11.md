# فحص شامل لقاعدة البيانات ومطابقة السياسات للواجهة

**التاريخ:** 2026-11-11
**المشروع:** `vqsvztudvfukyuerzcgx` (brc) — سكيما `brc`
**المنهج:** جرد كامل من `pg_catalog` + استدعاءات فعلية بدور `anon` + مطابقة كل سياسة مع حراسة `store.js` والواجهة.

---

## ١) الخلاصة التنفيذية

| البند | النتيجة |
|---|---|
| جداول السكيما | ٢٠ — **كلها RLS مفعّل** |
| سياسات RLS | ١٨ على ٦ جداول؛ ١٤ جدولاً بلا سياسة = **بلا أي صلاحية للمتصفح** |
| صلاحيات `anon` | **صفر** على كل الجداول العشرين (SELECT/INSERT/UPDATE/DELETE) |
| دوال `SECURITY DEFINER` | ٤٤ — **كلها** بلا استثناء تحمل `search_path` مثبّتاً |
| `service_role` أو كلمة مرور في المستودع | **لا شيء** — المفتاح العام فقط |
| مشاهد تتجاوز RLS | `public_jobs` عمداً — أعمدة صاحب العمل غائبة تماماً |
| مخزون ملفات (Storage) | صفر bucket — لا سطح هجوم |

**الحكم: لا توجد ثغرة حرجة أو عالية.** وجدت **ملاحظتين متوسطتين** وثلاث ملاحظات منخفضة، مفصّلة أدناه.

## ٣) الملاحظات

### م١ — القاعدة تسمح للموظف بالإدراج/التعديل، الواجهة تمنعه «بالمدير فقط»

**الوصف:** سياسات `jobs_staff_write` و`jobs_staff_update` و`applicants_staff_insert` تقبل `is_staff()` (أي الموظف والمدير). لكن دوال المتجر `createJob` و`updateJob` و`setJobStatus` و`createCardBatch` تحمل `if (!isAdmin())`.

**الخطورة:** متوسطة — **ليست ثغرة**، لأن الواجهة هي الأضيق. لكنها تعني:
- الموظف الذي يستدعي القاعدة مباشرة (F12) **يستطيع** إنشاء/تعديل وظيفة، بينما الزر مخفي عنه.
- الحماية قائمة على إخفاء الزر لا على منع العملية — وهو ضد المبدأ الذي بنينا عليه `deleteJob` هذه الجولة.

**الأثر على المستخدم:** لا يستطيع الموظف إيذاء البيانات (هو موظف موثوق، و`audit_log` يسجّل كل شيء باسمه). لكن **السلوك غير متسق**: الحذف مسموح له صراحةً، والإدراج ممنوع عنه في الواجهة ومسموح في القاعدة.

**إثبات عملي (نُفِّذ داخل معاملة أُلغيت):**
```sql
begin; set local role authenticated;
select set_config('request.jwt.claims',
  '{"sub":"862d785b-…","role":"authenticated"}', true);   -- محمد، موظف
insert into brc.jobs (code,title,employer_name,employer_phone)
  values ('ZZ-PROBE-01','probe','probe','07700000000');
-- → probe_inserted = 1   ← نجح الإدراج!
rollback;
```
بعد الإلغاء: ٢١ وظيفة، صفر بقايا. وفي المقابل بدور `anon`:
```sql
set local role anon;
insert into brc.jobs …;
-- → ERROR 42501: permission denied for table jobs
```
أي أن **الزائر محجوب على مستوى GRANT نفسه** قبل أن يصل إلى RLS أصلاً — حماية مزدوجة.

**الخيارات:**
- **(أ) تشديد القاعدة** لتطابق الواجهة: `jobs_staff_write`/`jobs_staff_update` → `is_admin()`. هذا يجعل الموظف لا يستطيع الإدراج/التعديل حتى مباشرةً. لكنه يقيّد مرونة مستقبلية.
- **(ب) توسيع الواجهة**: السماح للموظف بالإضافة/التعديل صراحةً (مثل الحذف). **هذا خيار المالك** — يحتاج قرارك.
- **(ج) تركها**: الواجهة هي الضابط، والسجل يسجّل كل شيء.

**التوصية:** (أ) — حتى يبقى مبدأ «القاعدة مطابقة للواجهة» سليماً، إلا إذا أردت أن يضيف الموظف وظائف بنفسه.

### م٢ — `customer_application_details` ترجع بيانات صاحب العمل الكاملة لمن يعرف (رقم بطاقة صحيح + رقم فرصة)

**الوصف:** دالة `SECURITY DEFINER` مفتوحة لـ`anon` بلا أي رمز تحقق. ترجع:
- **بيانات الباحث كاملة**: الاسم الثلاثي، الهاتف، العنوان، تاريخ الميلاد، الجنس، الجنسية
- **بيانات صاحب العمل**: الاسم، **الهاتف**، العنوان، **مكان المقابلة**، الراتب، الدوام

**الإثبات العملي (نُفِّذ بدور `anon` فعلياً):**
```
serial = '6F2JSP7P3C', attempt = 1
→ fullName: "حسين علي احمد"          ← بلا تعمية
→ phone:    "07715966434"            ← بلا تعمية
→ employerName:  "شركة آفاق النقل"
→ employerPhone: "07715993271"       ← مكشوف
→ interviewLocation: "المحاوليل - مقابلة مديرية النقل"  ← مكشوف
```

**لماذا هذا خطير أكثر من `self_service_card`:** بقية الدوال العامة إما تعمّي البيانات (`mask_name`/`mask_phone`) أو لا ترجع بيانات صاحب العمل أصلاً. هذه الوحيدة التي ترجع **هاتف صاحب العمل ومكان المقابلة** — وهما بالضبط العمودان المحجوبان في `public_jobs`.

**مقايضة التصميم:** الزائر **يحتاج** هذه الدالة ليعرف أين يذهب للمقابلة بعد التقديم. لا يمكن سحبها بلا كسر المسار.

**الخطر الفعلي:** منخفض عملياً — رقم البطاقة ١٠ خانات من أبجدية ٣١ حرفاً (≈ ٨×١٠¹⁴ احتمالاً) عشوائي بالكامل، والتخمين مستحيل. لكن من يرى بطاقة شخص آخر (صديق، قريب، بطاقة ملتقطة) **يحصل على بياناته كاملة** بلا أي رمز على ظهر البطاقة — وهذا يخالف مبدأ «البصمة على ظهر البطاقة هي المفتاح» الذي تتبعه `verify_form`.

**التوصية:** إضافة `p_token` اختياري (بصمة ظهر البطاقة) — إذا غاب، تُقنَّع بيانات الباحث و**يُحجب** هاتف صاحب العمل مع إبقاء مكان المقابلة (لأن الباحث يحتاجه). أو إبقاء الحال مع وعي بالمقايضة.

---

### م٣ (منخفضة) — `self_service_card` ترجع الملف الشخصي كاملاً بلا تعمية

ترجع `profile` = `self_application_data` (الاسم، الهاتف، العنوان، تاريخ الميلاد) لأي زائر يعرف رقم البطاقة. **لا ترجع بيانات صاحب العمل.**

رقم البطاقة عشوائي ١٠ خانات، فالمخاطرة عملية التخمين صفر. لكن نفس ملاحظة م٢: من يرى البطاقة يحصل على بيانات صاحبها.

---

### م٤ (منخفضة) — ثلاث دوال بـ`GRANT` صريح لـ`anon` لكنها ترفض داخلياً

`release_hold` و`set_outcome` و`select_attempt` كانت تُظهر `anon` فقط لأن ACL يحوي `authenticated` لا `anon`. تحققت من الكود: **كلها تبدأ بـ`if not brc.is_staff() then return ... 'غير مصرّح'`**. أي أنها محمية مرتين (الصلاحية + الحارس الداخلي). **لا إجراء مطلوب.**

---

### م٥ (منخفضة) — `employer_*` جداول يتيمة بلا سياسات ولا صلاحيات

`employer_job_credentials`, `employer_login_budget`, `employer_otp` تحتوي `pin_hash`/`code_hash`/`session_hash`. **لا سياسات، ولا صلاحيات لأي دور متصفح، ولا وصول للزائر.** بوابة واتساب القديمة متقاعدة وفق `docs/employer-job-pin.md`. **آمنة لكنها مساحة ميتة.**

**التوصية النهائية قبل التسليم:** إبقاؤها لا يضر (صفر صلاحيات). حذفها في جولة تنظيف منفصلة إن أردت تقليل سطح الهجوم البصري.

## ٤) ما تحقّق أنه سليم

| الفحص | النتيجة |
|---|---|
| RLS مفعّل على كل جدول | ✅ ٢٠/٢٠ |
| `anon` يقرأ جداول الموظفين | ❌ صفر صلاحية — لا SELECT على أي جدول |
| `public_jobs` تكشف اسم/هاتف صاحب العمل | ❌ الأعمدة غائبة تماماً من تعريف المشهد |
| `public_jobs` تكشف مكان المقابلة | ❌ غائب |
| `verify_form` بلا بصمة | ✅ تُعمّي الاسم والهاتف (`ح•••••••••` / `0771•••••34`) |
| `verify_form` ترجع `chance_code` بلا بصمة | ❌ `null` |
| `lookup_card` | ✅ تُعمّي الاسم والهاتف |

| كلمة مرور قاعدة في المستودع | ❌ |
| Storage buckets | ❌ صفر |

## ٦) ما يحتاج قرارك

1. **م١** — الموظف: هل يضيف/يعدّل وظائف بنفسه (توسيع الواجهة)، أم نمنعه في القاعدة (تشديد)؟ **حالياً: الواجهة تمنعه والقاعدة تسمح.**
2. **م٢** — `customer_application_details`: هل نضيف بصمة ظهر البطاقة، أم نبقيها مفتوحة (الزائر يحتاجها للمقابلة)؟

الباقي (م٣، م٤، م٥) لا يحتاج إجراءً للتسليم.
