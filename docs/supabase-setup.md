# ربط المنصة بـ Supabase — الخطوات وما أحتاجه منك

**الغرض:** تجهيز قاعدة البيانات على Supabase وتشغيل `docs/schema.sql` بنجاح.
> ✅ ملف المخطط **مُصلَّح ومتحقَّق منه** — يعمل الآن (`npm run test:schema` → 35/35).

---

## ⚠️ اقرأ هذا أولاً: لا ترسل المفاتيح في المحادثة

المطلوب منك **قيمتان عامّتان** تُنسخ كنص عادي، و**سرّ واحد تولّده أنت**:

| القيمة | عامّ أم سرّي؟ | تُرسل لي؟ |
|---|---|---|
| `Project URL` | عامّ | ✅ نعم |
| `anon public key` | عامّ (مصمَّم للنشر مع RLS) | ✅ نعم |
| `service_role key` | 🔴 **سرّي تماماً** | ❌ **أبداً** |
| `app.brc_secret` | 🔴 **سرّي** | ❌ **أبداً** — تضبطه أنت في Supabase |

`service_role` تتجاوز كل سياسات RLS — إذا تسرّبت، بيانات الباحثين وأرقام هواتفهم مكشوفة للجميع.
ضعها في متغيّرات بيئة على الخادم فقط، ولا تضعها في أي ملف داخل المستودع.

(هذا الدليل لا يطلب أي مفاتيح منك الآن — أنت تضبطها بنفسك وتخبرني فقط أن الخطوات تمّت.)

## 0) ⚠️ تكاملة GitHub — اقرأ هذا قبل أي شي

المشروع مربوط بالمستودع عبر **Supabase GitHub Integration**. هذا جيد ومفيد، لكن:

### ماذا تسوي هذه التكاملة؟

| | |
|---|---|
| **تقرأ** | ملفات `supabase/migrations/*.sql` من المستودع |
| **تُطبّق** | الـ migrations الجديدة على قاعدة الإنتاج **عند الدمج في `main`** |
| **لا تفعل** | لا ترفع أسراراً للمستودع · لا تكشف قاعدة البيانات · لا تُعدّل شيئاً غير المخطط |

> 💡 **الأمان:** المستودع **عام**، والتكاملة تقرأه فقط. لكن هذا يعني أن **أي ملف migration سيصير مرئياً للجميع** — فلا تضع فيه سرّاً أبداً (`app.brc_secret` يبقى خطوة يدوية).

### 🔴 لا تُفعّل «Branching»

| الخيار | التكلفة | التوصية |
|---|---|---|
| **Deploy to production** | ✅ مجاني في كل الخطط | **فعّله** |
| **Branching** (فرع معاينة لكل PR) | 🔴 **خطة Pro + يُحاسب بالساعة وخارج سقف الصرف** | ❌ **اتركه مغلقاً** |

### إعداد «Working directory»

سوبابيس تدور على مجلد `supabase/`. عند ضبط التكاملة يجب أن يكون:

```
Working directory = .        (نقطة — أي: المجلد الجذر للمستودع)
```

لأن مجلدنا في: `<repo root>/supabase/` ✅

### كيف صار نشر المخطط الآن؟

المخطط صار في **مكانين متطابقين** (وفحص آلي يمنع انحرافهما):

```
docs/schema.sql                                          ← المصدر (للقراءة والمراجعة)
supabase/migrations/20260915000000_brc_initial_schema.sql ← اللي تُطبّقه سوبابيس
```

**عند دمج هذا الفرع في `main`** → سوبابيس تُطبّق المخطط على قاعدة الإنتاج **تلقائياً**.
يعني **ما تحتاج تلصق الملف بيدك في SQL Editor** (§5 يصير بديلاً احتياطياً فقط).

> ✅ **إعادة التطبيق آمنة:** المخطط `idempotent` بالكامل (`if not exists` · `create or replace` · `drop policy if exists`) — فلو كنت نفّذته يدوياً سابقاً، إعادة تطبيقه لا تُفسد شيئاً ولا تمسح بيانات.

**عند أي تعديل مستقبلي على المخطط:**
```bash
npm run schema:sync     # ينسخ docs/schema.sql → ملف الـ migration
npm run test:schema     # يفشل إذا انحرفا
```

## 1) إنشاء المشروع

1. ادخل [supabase.com](https://supabase.com) → **New project**
2. اختر: الاسم، كلمة مرور قاعدة البيانات (احفظها في مدير كلمات المرور)، وأقرب منطقة
   (اختر **Europe** أو **Middle East** — الأقرب للعراق = استجابة أسرع)
3. انتظر ~2 دقيقة حتى يجهز

> 💡 **الخطة:** المجانية كافية للبداية، لكنها **تُنيم المشروع بعد 7 أيام خمول**
> (يستيقظ تلقائياً عند أول طلب، لكن أول طلب يتأخر ثوانٍ). إذا المنصة ستُستخدم يومياً فلا مشكلة.

---

## 2) تفعيل الامتدادات — ⚠️ خطوة إلزامية

`Database` → `Extensions` — فعّل:

| الامتداد | لماذا | إذا نسيتها |
|---|---|---|
| **`pg_cron`** | الإفراج التلقائي كل دقيقة (24 ساعة حجز + انتهاء استمارات) | الحجوزات تبقى معلّقة للأبد بلا تحرير تلقائي |
| **`pgcrypto`** | توقيع HMAC للبصمة المطبوعة في الكيو آر كود | يفشل فحص الكيو آر كود كلياً |

> المخطط صار لا يُسقط نفسه إذا كانتا غير مفعّلتين — بل يطبع تنبيهاً واضحاً. لكن التفعيل ضروري للوظائف.

---

## 3) توليد مفتاح البصمة — ⚠️ إلزامي

البصمة (`t=`) المطبوعة في الكيو آر كود تُوقَّع بمفتاح سرّي. **لا يوجد مفتاح افتراضي في الملف**
(كان سابقاً `BRC-BABIL-2026` مكتوباً في المستودع = أي شخص يقدر يزوّر البصمة).

**ولّد مفتاحاً قوياً** — من جهازك:
```bash
openssl rand -hex 32
```
ينتج شيئاً كهذا: `a3f1...` (64 حرفاً). **لا ترسله لي ولا تضعه في المستودع.**

ثم في Supabase: `Project Settings` → `Database` → **Custom settings**، أضف:
```
app.brc_secret = <المفتاح الذي ولّدته>
```
أو عبر SQL Editor:
```sql
alter database postgres set app.brc_secret = 'المفتاح_هنا';
select pg_reload_conf();
```

> ⚠️ بدون هذه الخطوة، `brc.verify_form` سترمي خطأ واضحاً ولن يعمل فحص الكيو آر كود.
> هذا **مقصود** (فشل مُعلَن أفضل من أمان وهمي).

## 4) كشف السكيما `brc` للواجهة — ⚠️ إلزامية

المخطط ينشئ كل شيء داخل سكيما اسمها `brc`. سوبابيس افتراضياً يكشف `public` فقط، فبدون هذي الخطوة
**الواجهة لا تقدر توصل لأي جدول إطلاقاً**.

`Project Settings` → `API` → **Exposed schemas** → أضف `brc` (بجانب `public`).

## 5) تشغيل المخطط

**الطريقة أ — تلقائية (موصى بها، لأن التكاملة مربوطة):**
ادمج الـ PR في `main` → سوبابيس تُطبّق `supabase/migrations/` تلقائياً.

**الطريقة ب — يدوية (بديل احتياطي):**
`SQL Editor` → **New query** → الصق **كامل** محتوى `docs/schema.sql` → **Run**

**النتيجة المتوقعة في الحالتين:** بلا أخطاء (قد تظهر `NOTICE` فقط). إذا ظهر خطأ فأرسله لي كما هو.

> ⚠️ **تحقّق بعد النشر التلقائي:** اذهب إلى `Database` → `Migrations` في لوحة سوبابيس،
> أو نفّذ: `select * from supabase_migrations.schema_migrations;`
> يجب أن ترى السطر `20260915000000`.
> إذا لم يُطبَّق، فالسبب غالباً **Working directory** غير مضبوط على `.` — راجع §0.

### تحقّق سريع بعد التشغيل
```sql
-- 1) الجداول الستة
select table_name from information_schema.tables
 where table_schema = 'brc' order by table_name;

-- 2) توليد الأكواد يعمل
select brc.next_job_code()     as job_code,
       brc.next_form_serial()  as serial;

-- 3) البصمة تعمل (يجب أن تُرجع 64 حرفاً hex — لو رجع خطأ فالمفتاح غير مضبوط)
select brc.verify_token('BRC-NO-000120');

-- 4) الإفراج التلقائي مجدول؟
select jobname, schedule, active from cron.job where jobname = 'brc-auto-release';
```

## 6) إنشاء مستخدَمي الدخول

`Authentication` → `Users` → **Add user** — أنشئ حساب المدير:
- بريد المدير (مثال: `admin@brc-babil.com`) + كلمة مرور قوية
- ✅ علّم **Auto Confirm User**

كرّر للباقي. **كل موظف بمستخدم خاص** — لأن سجل التدقيق يسجّل الفاعل، والمستخدم المشترك
يبطل معنى التدقيق.

⚠️ **لا تستخدم** البريد الإلكتروني كاسم مستخدم في الكود — التسجيل بـ Auth عبر **البريد**،
وملف `brc.staff` فيه عمود `username` منفصل للعرض.

### ثم اربطهم بالجدول (SQL Editor)
```sql
insert into brc.staff (auth_id, username, full_name, role, job_title, phone)
select id, 'admin', 'المدير العام', 'admin', 'الإدارة العامة', '07760058007'
  from auth.users where email = 'admin@brc-babil.com'
on conflict (username) do update set auth_id = excluded.auth_id;

-- كرّر لكل موظف مع role = 'staff'
```

**⚠️ مهم:** من لا سطر له في `brc.staff` **لا يستطيع فعل أي شيء** — كل دوال الصلاحية
تُقرأ من هذا الجدول. هذه هي الحماية الأساسية.

## 7) تحقّق نهائي من RLS

```sql
-- يجب أن ترى 6 جداول و rowsecurity = true لكلها
select relname, relrowsecurity from pg_class
 where relnamespace = 'brc'::regnamespace and relkind = 'r';

-- عدد السياسات لكل جدول (لا جدول بلا سياسة)
select tablename, count(*) from pg_policies
 where schemaname = 'brc' group by tablename order by tablename;
```

## 9) ماذا يحدث بعد ذلك (من جهتي)

بعد ما تعطيني `Project URL` + `anon key`، التالي:

1. إضافة `supabase-js` للصفحات (CDN + دمج في الملف المستقل عبر `tools/build.mjs`)
2. طبقة الربط داخل `assets/js/store.js`:
   - تحميل الجداول مرة عند الإقلاع → نفس كائن `db` في الذاكرة → **الواجهة ترسم كما هي**
   - الكتابة: تحديث محلي فوري + إرسال لسوبابيس + `emit()`
   - **Realtime**: اشتراك يحدّث `db` عند تغيير أي مستخدم آخر
3. تحويل 5 عمليات إلى نداءات RPC (لأن الحماية فيها):
   `select_attempt` · `set_outcome` · `release_hold` · `verify_form` · `run_auto_release`
4. تبديل الدخول من `CFG.users` (كلمات مرور مكشوفة في JS!) إلى `supabase.auth.signInWithPassword`
5. إعادة تصميم النسخ الاحتياطي — نظام `localStorage` الحالي يفقد معناه، والنسخ تصير من قاعدة البيانات
6. تحديث الاختبارات + بناء الملف المستقل

> **ملاحظة أمنية:** كلمات المرور الحالية (`admin/admin123`) مكتوبة في `assets/js/config.js`
> ومكشوفة لأي زائر يفتح «عرض المصدر». هذا مقبول كنسخة عرض، لكن **لا يجوز النشر العام قبل
> الربط بـ Auth**.
