# بوابة صاحب العمل — رمز واتساب وكود الوظيفة

## الحالة الفعلية

**الكود جاهز للاختبار المحلي فقط، ولا يوجد مزوّد إرسال مفعّل من هذه الجلسة. لم يُرسل رمز واتساب حقيقي، ولم تُنشر الواجهة أو Edge Function، ولم تُطبّق الهجرة على الإنتاج.** يلزم اعتماد الإعدادات والقالب وحساب WhatsApp Business ثم اختبار تسليم فعلي على رقم صاحب عمل مخوّل. عدم توفر الخدمة يُظهر خطأ صريحاً ولا ينقل المستخدم إلى شاشة «تم الإرسال» الوهمية.

## الرحلة

زر «صاحب العمل؟ دخول آمن برمز واتساب» في صفحة مسح البطاقة يفتح `employer.html?form=...`. كذلك مداخل صاحب العمل القديمة في الموقع السحابي تتحول للبوابة الجديدة. عروض الملفات المحلية التجريبية بلا خادم تحتفظ بمسارها المحلي؛ لا تُستخدم كتحقق إنتاج.

1. رقم البطاقة يأتي من الرابط، ويكتب صاحب العمل **كود وظيفته** المطبوع بالاستمارة.
2. الخادم يربط البطاقة بالتقديم والوظيفة، ويأخذ رقم صاحب العمل من **سجل الوظيفة فقط**. لا يختار المستخدم رقم الإرسال. الأرقام العراقية تُوحّد لصيغة `9647...`؛ الرقم المفقود/غير الصالح يمنع الإرسال.
3. رمز عشوائي من ستة أرقام عبر قالب Authentication في واجهة Meta WhatsApp Cloud API، بصلاحية خمس دقائق. أرقام عربية أو فارسية في الحقل تُحوّل إلى أرقام قياسية.
4. بعد التحقق: جلسة عشوائية 256-bit لعشرين دقيقة، مرتبطة **بالتقديم المحدد**، وليس أحدث وظيفة على البطاقة. تعرض اسم المتقدم وهاتفه وسكنه وجنسه ووظيفة صاحب العمل فقط.
5. يمكن طلب تثبيت التوظيف أو تسجيل عدم التوظيف بسبب واضح. التوظيف ينتظر تثبيت الشركة؛ الرفض يجعل الوظيفة حرجة معلّقة دون إعادة فرصة أو تحرير تلقائي. القرار لا يتكرر.
6. إنهاء الجلسة يلغيها بالخادم. الرمز والجلسة في ذاكرة الصفحة فقط، لا في URL أو localStorage/sessionStorage. تغيّر رقم صاحب العمل في الوظيفة يبطل وصول الجلسة السابقة.

## قبل أي نشر

**انشر الهجرة والبوابة وEdge Function كترقية متكاملة بعد الموافقة؛ لا تطبّق الهجرة منفردة وأنت تعتمد صفحة صاحب العمل القديمة، لأنها تغلق مداخلها غير المتحققة. لا تعِد تطبيق ملفات تحديث الباركود التاريخية أو نسخ SQL القديمة بعد الهجرة الجديدة لأنها قد تعيد منح صلاحيات المداخل القديمة. رسالة الخطأ العامة توجّه إلى الهجرات الحديثة بدلاً من أداة اللصق التاريخية غير المشمولة بالتوزيع.**

- الهجرة: `supabase/migrations/20261017150000_employer_whatsapp_otp.sql`، مطابقة للجزء المضاف إلى المصدر `docs/schema.sql` والملف الأساسي المتزامن.
- الدالة: `supabase/functions/hrc-employer-otp/index.ts`، باسم `hrc-employer-otp`، معلنة في `supabase/config.toml`. `verify_jwt=false` مقصود لبدء التحقق العام؛ صلاحية عرض/قرار صاحب العمل تأتي من جلسة OTP لا من JWT الزائر.
- الصفحة والأصول: `employer.html` و`assets/css/employer.css` و`assets/js/employer.js`. مجلد النشر وكاش v30 يشملانها.
- تأكد من إتاحة سكيما `brc` في PostgREST كما في إعداد المشروع القائم. الـRPCs الجديدة تمنح `service_role` فقط، ولا تُمنح للمتصفح.

### إعداد Meta ومتغيرات البيئة — على الخادم حصراً

يلزم حساب WhatsApp Business فعلي، رقم إرسال مسجّل ومخوّل، رمز وصول مناسب بصلاحيات الإرسال، وقالب **Authentication** معتمد يدعم زر نسخ الرمز، بلغة مطابقة. يجب مراجعة أهلية الحساب والرقم والتسعير والسياسات والتسليم لأرقام العراق لدى Meta؛ لم نتحقق منها حياً هنا.

أضف الأسرار من إعدادات Edge Function، **لا في المحادثة أو ملفات Git أو الواجهة**:

- `WHATSAPP_ACCESS_TOKEN`: رمز الوصول الخاص بالإرسال.
- `WHATSAPP_PHONE_NUMBER_ID`: معرّف رقم الإرسال، وليس رقم الهاتف نفسه.
- `WHATSAPP_OTP_TEMPLATE`: اسم قالب Authentication المعتمد.
- `WHATSAPP_OTP_LANGUAGE`: لغة القالب، الافتراضي `ar`؛ يجب أن تطابق اعتماد Meta حرفياً.
- `WHATSAPP_GRAPH_VERSION`: نسخة Graph API المدعومة للحساب، الافتراضي `v23.0`؛ تحقق من النسخة عند النشر.
- `EMPLOYER_OTP_SECRET`: سر عشوائي قوي لا يقل عن 32 حرفاً لتوقيع HMAC؛ لا تستخدم كلمة مرور بشرية. تغييره يلغي صلاحية الأكواد والجلسات السابقة عملياً.
- `EMPLOYER_ALLOWED_ORIGINS`: أصول الموقع المعتمدة مفصولة بفواصل، بلا مسارات وبلا `*`، مثال أصل الموقع الرسمي فقط. لا تضف أصل معاينة إلا عند الحاجة ثم أزله.
- `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY`: من بيئة Supabase الخادمية. مفتاح الخدمة لا يخرج إلى المتصفح مطلقاً.

قبول Meta للرسالة لا يثبت وصولها للهاتف. الواجهة تقول «تم قبول طلب إرسال الرمز» فقط. التحقق الحي المطلوب يشمل استلام الرمز، انتهاءه، والربط الصحيح بالوظيفة عند وجود تقديمين.

## الحدود والحماية

- لا يُخزّن OTP الخام؛ يُخزّن HMAC مربوط بمعرّف تحدٍّ عشوائي. لا يُعاد الرمز أو رقم صاحب العمل أو تفاصيل أخطاء المزوّد للمتصفح، ولا تُكتب الأسرار في السجلات.
- خمس محاولات تحقق فقط لكل تحدٍّ، محمية بقفل صف؛ الرفض يزيد العداد فعلياً. الرمز يستخدم مرة واحدة.
- إعادة إرسال بعد 60 ثانية، بحد ثلاثة طلبات لكل رقم/ساعة وعشرة/يوم؛ عشرة لكل بصمة IP/ساعة، وسقف تكلفة محافظ 200 طلب إرسال إجمالي/يوم. تعديلات الحدود تستلزم مراجعة التكلفة. IP يُوقّع ولا يُخزّن خاماً؛ حدود الرقم والسقف العام لا تعتمد على مصداقية ترويسة IP وحدها.
- الإرسال الجديد يبطل الأكواد غير المتحققة السابقة لنفس الطلب، **ولا يسمح لطالب رمز جديد بإلغاء جلسة صاحب عمل متحقق**.
- عدم قبول المزوّد أو خطأ الإرسال يبطل التحدي. طلب فاشل يُحتسب ضمن الحدود لمنع إعادة المحاولة المكلفة بلا حد.
- جدول OTP مفعّل عليه RLS وبلا صلاحيات قراءة/كتابة للزائر أو authenticated. كل RPC جديد خدمة فقط. تُغلق كذلك **كل تواقيع ونسخ employer_view/employer_decide القديمة** أمام PUBLIC وanon وauthenticated لمنع تجاوز البوابة.
- البيانات قصيرة العمر تُحذف بعد يومين أثناء الإصدار، ولا تُستخدم كسجل تدقيق دائم؛ قرارات التوظيف تسجّل في سجل التدقيق القائم بلا رمز أو توكن.
- بوابة OTP لا تغيّر سياسة قراءة صاحب البطاقة العامة (`self_service_card`) أو فرصه أو أكواد البطاقة. ليست إعادة تصميم شاملة لسرية جميع صفحات الباركود، ولا تصحح قرارات سابقة.

## الاختبارات

`npm run test:employer-otp`: تعريفات SQL الحقيقية في PostgreSQL معزول، وكل صلاحيات الأدوار والتواقيع القديمة، ربط الوظيفة الأولى حتى عند وجود ثانية، حدود المحاولات/الإعادة، انتهاء الأكواد والجلسات، تغيّر رقم صاحب العمل، قرارات محصورة بوظيفة واحدة، دالة Edge TypeScript الحقيقية مع HTTP/crypto ومزوّد/قاعدة وهميين، وواجهة DOM الفعلية بما فيها فشل المزوّد وعدم وجود إرسال وهمي وتطبيع الأرقام وحقن HTML. **هذه اختبارات محلية وليست اختبار إرسال Meta حقيقي.** اختبارات الحسابات السحابية لم تُضعف أو تُعطّل.

فحص Chromium محلي على 320 و375 و768 و1440 و1920px شمل المراحل الثلاث (15 حالة) بلا تجاوز أفقي أو أخطاء JavaScript. كل طلبات الإرسال والتحقق في هذا الفحص وهمية. `npm run dist` يفحص أن الصفحة وأصولها المحلية مشمولة بمجلد النشر النظيف.

نتيجة التحقق لهذا التغيير: **39 اختبار OTP**، و**15 حالة عرض Chromium**، و`test:all` بلا إخفاقات، والبناء الكامل والخفيف و`dist` ناجحة. ملخّص المدقق العام 140 نجاحاً مع ثلاثة تحذيرات قائمة (أيقونة غير مستخدمة وصور العرض الخارجية بالملفين المستقلين). لم تُنفّذ أي كتابة على قاعدة الإنتاج أو إرسال مزوّد حي أو نشر من الجلسة.

## تصحيح إعادة المسح وتشخيص Failed to fetch

- بعد استهلاك فرص البطاقة المؤكدة من `self_service_card`، تعرض `apply.html` مدخل صاحب العمل فقط، بلا بدء تقديم وبلا كشف أسماء المتقدم أو الوظائف. لا تُزاد الفرص ولا تُنشأ بطاقة جديدة. البطاقة ذات الفرصة الواحدة تبقى بمسار اختيار الوظيفة المتبقية، وذات الفرصتين تبقى بمسار البداية.
- بطاقة مكتملة تبقى قابلة لمتابعة صاحب العمل حتى لو تعذّر جلب قائمة الوظائف العامة. حالات صفر الفرص بلا تقديم مسجّل تبقى خطأ بيانات يستلزم مراجعة، ولا تعامل كفرص جديدة.
- كانت قائمة `EMPLOYER_ALLOWED_ORIGINS` الفارغة ترفض preflight قبل إرسال رسالة عدم التفعيل، فيخفي المتصفح سبب الخطأ وراء Failed to fetch. الآن preflight لا يرسل بيانات ولا ينفذ إجراء؛ الاستدعاء الفعلي يظل ممنوعاً حتى التهيئة. ردود الرفض فقط تسمح بقراءة التشخيص عبر CORS؛ **لا يمنح ذلك مصدراً مرفوضاً حق إرسال رمز أو عرض طلب أو اتخاذ قرار**.
- فشل fetch يُشرح بالعربية دون الادعاء أن رسالة أُرسلت أو لم تُرسل؛ لا يمكن استنتاج التسليم من انقطاع الاتصال، ولا يُعاد POST تلقائياً تفادياً لإرسال مكرر. رد 404 يوضح أن الدالة غير منشورة. حالات 401/403 البوابية توضّح ضرورة فحص صلاحية الخدمة والنطاق.
- لا تثبت هذه التصحيحات حالة الخادم الحي. لم نصل لحساب Meta أو إعدادات Supabase الخاصة ولم نرسل رسالة فعلية. تفعيل التسليم يحتاج حساب Meta وقالب Authentication معتمد وأسرار الخادم المذكورة أعلاه، نشر الهجرة والدالة مع `verify_jwt=false`، وإضافة **أصل الموقع الفعلي** لقائمة النطاقات، ثم اختبار تسليم مخوّل.
- الاختبارات الجديدة: `npm run test:employer-entry` (14 حالة مسح/فرص/تعطل قائمة الوظائف)، و`npm run test:employer-otp` (44 حالة بما فيها CORS غير المهيأ، منع المصدر الأجنبي، وانقطاع fetch والدالة غير المنشورة). اختبارات محلية بلا إرسال حي.
