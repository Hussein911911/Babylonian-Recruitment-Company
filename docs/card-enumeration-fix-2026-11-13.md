# إغلاق تعداد البطاقات وكشف بيانات الباحثين

**التاريخ:** 2026-11-13
**الترحيل:** `supabase/migrations/20261113170000_card_enumeration_guard.sql`
**الفحص الدائم:** `tests/card-enumeration.mjs` (27 فحصاً) — `npm run test:enumeration`

---

## ١. ما كان يحدث

الثغرة **لم تكن احتمالاً** — نُفِّذت فعلياً على قاعدة PGlite بنفس سلسلة الترحيلات:

```
anon → brc.lookup_card('HRC-BC-900001'::text, null::text)
     → {"ok":true,"fullName":"غيث حماد عبد الصاحب","phone":"07800977448", …}
```

وبمسح ٤٠ رقماً متتالياً (`HRC-BC-900001` … `HRC-BC-900040`): **٤٠/٤٠ انكشفت**.

ثلاثة عناصر جعلت الأثر عملياً لا نظرياً:

1. **أرقام البطاقات شبه متسلسلة ومطبوعة** على البطاقة نفسها.
2. **المفتاح العام منشور** في `assets/js/supabase-config.js` — أي زائر يملكه.
3. **لا حدّ طلبات**: `brc.card_gate` موجودة (٦٠/دقيقة + قفل ١٠ دقائق) لكن
   `lookup_card` **لا تستدعيها إطلاقاً**.

## ٢. السبب الجذري

سطر واحد في `lookup_card` و`self_service_card`:

```sql
if v_stored = '' then
  v_ok := true;   -- ← كان
```

`v_stored` هو `card_print_code`. **كل** بطاقات اليوم بلا رمز طباعة، فالشرط صحيح
دائماً، فـ`v_ok` صحيح دائماً، فتُرجع الدالة الاسم والهاتف كاملين بلا أي إثبات
حيازة. و`mask_name`/`mask_phone` مكتوبتان في المخطط لهذا الغرض بالضبط — لكن
شرط تفعيلهما كان لا يتحقق في الإنتاج أبداً. تعليق الكود يقول «بيانات مقنّنة»
والسلوك يقول العكس؛ ولهذا لم يكشفه أي فحص نصّي.

## ٣. الحل: غلاف لا إعادة كتابة

الجسمان المجرَّبان أُعيدت تسميتهما إلى `*_unguarded`، ووُضع غلاف بالتوقيع
**نفسه** `(text, text)` — فلا تتغيّر أي واجهة، ولا يُمَس منطق مُختبَر:

```
الزبون ──> lookup_card(text,text)          ← الغلاف: حارس + تقنين
                └──> lookup_card_unguarded ← الجسم القديم كما هو
```

**لماذا لا وسيط ثالث؟** توقيعان بنفس الاسم أحدهما بقيمة افتراضية يجعل النداء
غامضاً (`function is not unique`) ويكسر `apply.html` بالكامل. الغلاف بالتوقيع
نفسه هو الطريق الوحيد الذي لا يغيّر عقد الواجهة.

### ٣.١ الحارس — `brc.card_lookup_guard`

| الحدّ | القيمة | الغرض |
|---|---|---|
| لكل بطاقة | ١٥ عرضاً/ساعة | يمنع مراقبة بطاقة واحدة |
| لكل مصدر | ٤٠ بطاقة مختلفة/ساعة | **هذا هو ما يوقف التعداد** |

المصدر يُقرأ من ترويسات PostgREST (`cf-connecting-ip` → `x-real-ip` →
`x-forwarded-for`) ويُخزَّن **بصمة `md5` فقط** في `brc.card_lookup_budget`.
لا IP خام، ولا معرّف جهاز، والجدول مغلق تماماً عن `anon`/`authenticated`
(RLS مفعّل، صفر منح) ويتنظّف تلقائياً بعد ساعتين.

### ٣.٢ التقنين

| | بلا رمز صحيح | بالرمز الصحيح |
|---|---|---|
| الاسم | `غيث ح.` | `غيث حماد عبد الصاحب` |
| الهاتف | `0780••••48` | `07800977448` |
| العلم | `masked:true` · `verified:false` | `masked:false` · `verified:true` |

`self_service_card` تُقنّع `card.profile` كذلك (الاسم، الهاتف، العنوان، الميلاد)
وتُقفل الملف بـ`profileLocked:true`.

### ٣.٣ السجل التدقيقي

مُشغِّل `trg_block_fingerprint_audit` يرفض أي سطر `details` يبدأ بـ
`lookup:` / `self_service:` / `fingerprint:` — كي لا تتسرّب البصمات عبر
`audit_log` إن أُضيف تدقيق لاحقاً.

## ٤. ما لم يُمَس (عن قصد)

- **لا `DELETE` ولا `UPDATE` على أي صف موجود.** لا بيانات زبون واحدة تغيّرت.
- **`apply_with_card` و`use_chance` و`customer_application_details`** كما هي.
- **`docs/schema.sql`**: الجسمان الأصليان **بلا تغيير** (`v_ok := true` باقٍ
  هناك). لماذا؟ لأن تغييره إلى `false` يُفرغ `card.profile` في الاستمارة،
  فيرى الزبون «غيث ح.» بدل اسمه فيكتب فوق بياناته — أي **تخريب بيانات حقيقي
  مقابل تقليل تسريب**. الحماية تأتي من الغلاف (الحارس) لا من إفساد مسار
  العرض. الفرق الوحيد في المخطط: إضافة `card_public_name` و`card_public_phone`.
- **`apply.html`**: إضافة عرض فقط — تنبيه `.masked-note` يطمئن الزبون أن
  بياناته محفوظة كاملة لدى الشركة ولا حاجة لإعادة كتابتها.
- **الرموز القديمة**: صالحة كما هي. البطاقة بلا رمز مطبوع تعمل كما كانت.

## ٥. الأثر على الزبون الحقيقي

| الحالة | قبل | بعد |
|---|---|---|
| زبون يمسح بطاقته ويقدّم | ✅ يعمل | ✅ يعمل (مُختبَر) |
| إعادة مسح بطاقة مستعملة | يرى اسمه | يرى «علي ح.» + تنبيه «بياناتك محفوظة لدى الشركة» |
| بطاقة فارغة | ✅ | ✅ (لا بيانات فيها أصلاً) |
| بطاقة برمز مطبوع + الرمز | بيانات كاملة | بيانات كاملة |
| زائر يعدّد الأرقام | **كل الأسماء والهواتف** | «غ ح.» فقط، ثم يُحجب |

آخر سطر هو المقايضة الوحيدة: الزبون الذي أعاد المسح يرى اسمه مقنّعاً حتى
يحضر للمقر. بديله كان ترك هواتف ٤٤٠ باحثاً مكشوفة للعالم.

## ٦. لماذا لا يمكن الاعتماد على رمز الطباعة وحده

`card_print_code` فارغ في **كل** البطاقات الحالية. لو شرطنا رمزاً لا يملكه
الزبون لأغلقنا التقديم على الجميع. لذلك: **الحارس هو الضمانة**، والتقنين
طبقة ثانية تعمل متى وُجد رمز مطبوع.
