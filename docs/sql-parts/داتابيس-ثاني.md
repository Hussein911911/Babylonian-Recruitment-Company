# هل نكدر نستخدم داتابيس ثاني؟ وهل نسختنا اعتمادية؟

## الجوابان — بجملتين

**١) نعم نكدر نستخدم أي قاعدة PostgreSQL — مو بس Supabase.**

**٢) نسختنا اعتمادية للبيانات — لكن استئناف الموقع يحتاج منك ٣ أشياء
لا تُنقل في ملف.**

---

## السؤال الأول: داتابيس ثاني؟

السكيما كلها في `brc` — قولب واحد. جرّبناها فعلياً على PostgreSQL عادي
بلا Supabase إطلاقاً:

| الخطوة | النتيجة |
|---|---|
| طبقة التوافق | ✅ |
| ٥ أجزاء هيكل | ✅ **١٩ جدولاً · ٦٦ دالة** |
| استرجاع ٧٢٤ بطاقة | ✅ ٧٢٤ · ١٤٤٨ محاولة |
| صفر مخالفات | ✅ |

**فأي مكان فيه PostgreSQL يقبل بياناتك:** Supabase آخر · Neon · Railway ·
سيرفر عندك · حتى جهازك.

### لكن — هنا الصراحة

القاعدة تُنقل. **الموقع لا ينتقل وحده.**

| ما يحتاجه الموقع | Supabase يوفّره | PostgreSQL عادي |
|---|---|---|
| تسجيل دخول | ✅ Auth | ❌ **ما موجود** |
| صور الوظائف | ✅ Storage | ❌ ما موجود |
| الإفراج التلقائي كل دقيقة | ✅ pg_cron | ⚠️ تحتاج مجدول |
| واجهة API جاهزة | ✅ PostgREST | ⚠️ تحتاج تركيب |

**النتيجة:** على PostgreSQL عادي، بياناتك **محفوظة وقابلة للقراءة** —
لكن الموظف ما يقدر يدخل، والعميل ما يقدر يمسح باركوده عبر الموقع.

**الاستئناف الحقيقي = مشروع Supabase آخر.** لأنه الوحيد الذي يعطي كل
الطبقات الأربع جاهزة في ١٠ دقائق.

---

## السؤال الثاني: هل النسخة اعتمادية؟

### ما **يُسترجَع** بالكامل ✅

| ما | الحالة |
|---|---|
| ٧٢٤ بطاقة (اسم، هاتف، عنوان…) | ✅ |
| ١٥٣٣ محاولة + أي وظيفة اختارها | ✅ |
| ٢٢ وظيفة + بيانات صاحب العمل | ✅ |
| أرقام البطاقات المطبوعة | ✅ |
| الحسابات (اسم، دور، صلاحية) | ✅ |
| سجل التدقيق (٣٧٧٥ حركة) | ✅ |
| الإعدادات | ✅ |
| سجل الفرص والطباعة | ✅ بعد إصلاح v3 |

### ما **لا يُسترجَع** — بصراحة ❌

| ما | لماذا | الحل |
|---|---|---|
| **كلمات المرور** | في `auth.users` — لا تُصدَّر (تصديرها خطر أمني) | تُعاد لكل موظف (٣ أشخاص) |
| **`app.brc_secret`** | سرّ توقيع — لا يوضع في ملف يُنشر | يُنسخ يدوياً من الإعدادات |
| **`anon key`** | خاص بالمشروع القديم | المفتاح الجديد |
| **صور الوظائف** | ملفات في Storage لا SQL | إعادة رفع (٤ صور) |
| **رابط الموقع** | في `supabase-config.js` | `npm run supabase:repoint` |

**لا شي من هذا «ضاع». كلها ٥ خطوات يدوية موثّقة.**

---

## ما **اكتشفناه اليوم** — وهذا أهم شي

### ١) عطل كان سيقتل الاسترجاع

زر «تنزيل الهيكل» في `restore.html` كان يعطي ملفاً **٣١٥٤ سطراً**.
ومحرّر Supabase يقصّ عند ٢٠٠٠ **ويرفع Success**. فتبني قاعدة **١١ جدولاً
من ١٩** وتظنها نجحت. ← **أُصلح: صار ٥ أجزاء تحت ٧٠٠ سطر.**

### ٢) عطل يُفقد بيانات فعلاً

`recovery_export_v2` — النسخة التي ينزّلها موقعك **الآن** — لا تصدّر
`recovery_chances`. لديك **٤٦ فرصة مستهلكة على ٣٠ بطاقة**.
بعد الاسترجاع تصير متاحة ← **العميل يعيد استخدام فرصة دفع ثمنها**.
← **أُصلح: `1-إصلاح-تصدير-النسخة.sql` (٨٩ سطراً).**

### ٣) عائق تبديل المشروع

معرّف المشروع مكتوب في **٢٠ موضعاً في ١٠ ملفات** — منها `_headers`
(سياسة CSP) و`sw.js`. من يعدّل ملف الإعدادات وحده يخرج بموقع **يفتح
ولا يتصل**، ويظن أن الاسترجاع فشل.
← **أُصلح: `npm run supabase:repoint`.**

## اعتمادية النسخة — بدرجة

| الجانب | الدرجة |
|---|---|
| البيانات تُسترجع | ✅ **٩٥٪** |
| الموقع يستأنف | ✅ **١٠٠٪** على مشروع Supabase |
| على PostgreSQL عادي | ⚠️ **٤٠٪** — بيانات بلا دخول |

**الـ٥٪ الناقصة:** كلمات المرور والسرّ. لا تُنقل لسبب أمني — لا لعطل.

---

## خلاصة الجواب

> **نعم نكدر نستخدم داتابيس ثاني — وبياناتك تنتقل كاملة.**
> **لكن الموقع ما يستأنف إلا على Supabase (أو ما يبنيه أحد مكانه).**
> **ونسختنا اعتمادية — أثبتناها على ٧٢٤ بطاقة.**
> **الفرق بين «اعتمادية» و«مُثبتة» هو أن تجرّبها بنفسك.**

## الترتيب عند الطوارئ — ٦ خطوات

```
١. مشروع Supabase جديد           → ١٠ دقائق
٢. فعّل pgcrypto + pg_cron
٣. الصق ٥ أجزاء الهيكل            → من restore.html
٤. الصق أجزاء البيانات            → من نسختك
٥. ألصق إصلاح التصدير             → ٨٩ سطراً
٦. npm run supabase:repoint <ref> <key>
   + app.brc_secret + كلمات المرور + الصور
```

بعدها: **قارن ٧٢٤ بطاقة**. لو طابقت — النسخة ناجحة.
