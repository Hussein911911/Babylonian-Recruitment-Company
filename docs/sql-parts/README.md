# لصق أجزاء SQL في محرّر Supabase — الدليل الكامل

> **لماذا هذا المجلد؟** محرّر SQL في Supabase لا يستقبل ملفاً واحداً بطول ٣٠٠٠+
> سطر: إمّا يرفض اللصق، أو تنتهي مهلة التنفيذ (‏**٦٠ ثانية** كحدّ أقصى في اللوحة)
> فيُلغى كل شيء. قسّمنا الملفات إلى أجزاء صغيرة، **كل جزء معاملة مستقلّة**،
> والنتيجة النهائية مطابقة تماماً للملف الأصلي — صفّاً بصفّ.

---

## ⚠️ عطلان حقيقيان أُصلحا في هذه الجولة

### ١) `docs/schema.sql` كان ناقصاً جدولين
كان ينشئ ١٦ جدولاً، وملف البيانات يحتاج ١٨. `brc.card_number_registry` و
`brc.card_number_counter` كانتا في ترحيل منفصل فقط. من يبني قاعدة من هذا
الملف وحده كان يفشل عند أول بطاقة:

```
ERROR: relation "brc.card_number_registry" does not exist
```

**أُصلحت المشكلة من جذرها:** الكتلة أُدمجت في `docs/schema.sql` نفسه (القسم
١٣)، فلم تعد هناك حاجة لملف إضافي. أُعيدت المزامنة والبناء تلقائياً.

### ٢) النسخة نفسها كانت تُسقط ٤ جداول عند الاسترجاع
`recovery_export_v2` تصدّر ١٠ جداول من ١٩. التفاصيل في قسم «فجوة» أدناه.

---

## 🔴 قبل كل شيء: أي ملفات تنزّل بالضبط

**السكيما جاهزة — لا تُولَّد.** البيانات **يجب** أن تُولَّد من نسختك أنت.

| # | تنزّل / تُولّد | من أين | عدد الملفات |
|---|---|---|---|
| ١–٥ | **السكيما** | `docs/sql-parts/schema/` (جاهزة في المشروع) | ٥ |
| ٦–… | **البيانات** | تُولَّد من `2-data.sql` عندك | ٨+ (حسب حجمك) |

> ⛔ **لا تلصق أي ملف بيانات من المستودع.** مجلد `data/` هنا محذوف عمداً
> ويحتوي تحذيراً فقط: ما كان فيه بيانات تجريبية كتبتُها للاختبار («باحث عن
> عمل ١»). لصقها على قاعدة فيها بياناتك **يمسحها كلها** ويضع ٤٤٠ بطاقة وهمية.

### توليد أجزاء البيانات (خطوة واحدة)

بعد فكّ التشفير في `restore.html` تحصل على `1-schema.sql` و`2-data.sql`.
ضع `2-data.sql` بجانب `package.json` ثم:

```bash
node tools/split-sql.mjs 2-data.sql --out docs\sql-parts\data
```

تخرج أجزاء `2-data-part-01.sql` … وبجانبها `INDEX-2-data.md` فيه خريطة اللصق
وأعدادك الحقيقية.

> ℹ️ `1-schema.sql` من نسختك **لا تحتاجه** — السكيما واحدة للجميع ومولَّدة
> أصلاً في `schema/`. لكن لو أردت التطابق التام:
> `node tools/split-sql.mjs 1-schema.sql --out docs\sql-parts\schema`

## الترتيب — لا تقفز واحدة

افتح **Supabase → SQL Editor → New query** لكل جزء. بعد `Success` انتقل للتالي.

### ① السكيما — `schema/` (٥ أجزاء)

| # | الملف | أسطر | يفعّل |
|---|---|---|---|
| ١ | `schema-part-01.sql` | 674 | الإضافات · الأنواع · الجداول الأولى · الفهارس · الدوال |
| ٢ | `schema-part-02.sql` | 660 | الدوال · العروض · الإعدادات الافتراضية |
| ٣ | `schema-part-03.sql` | 684 | جداول إضافية · سياسات RLS |
| ٤ | `schema-part-04.sql` | 688 | الدوال الأمنية · المشغّلات · المهام المجدولة |
| ٥ | `schema-part-05.sql` | 480 | الفهارس الأخيرة · منح `service_role` · تقنين البيانات |

> ⏱ **تنبيه:** الجزء الأخير فيه `select brc.archive_finished_cards();` — قد
> يستغرق وقتاً على قاعدة كبيرة. إن ظهر `canceling statement due to statement
> timeout`، **فالجزء نجح فعلياً** (الخطأ في السطر الأخير فقط)، وتابِع. أو
> شغّل ذاك السطر وحده لاحقاً.

### ② البيانات — `data/` (تُولَّد من نسختك)

العدد يعتمد على حجم بياناتك: ٤٤٠ بطاقة ⇐ ٨ أجزاء، ٦٠٠٠ بطاقة ⇐ ٦٩ جزءاً.
كل الأجزاء تحت ٧٠٠ سطر. الأسماء متتالية `2-data-part-01.sql` فما فوق،
والترتيب الرقمي هو ترتيب اللصق.

> الأعداد المتوقّعة **لك** مكتوبة أعلى الجزء الأول في سطر «الأعداد» —
> قارن بها بعد الانتهاء، لا بأعداد هذا الدليل.

> ⚠️ **الجزء ٦ يُفرّغ الجداول** (`TRUNCATE`). لا تشغّله على قاعدة فيها بيانات
> حقيقية. لو كانت قاعدة الإنتاج مليئة، أوقف هنا وأخبرني.

## لماذا «كل جزء معاملة مغلقة»؟

الملف الأصلي يبدأ بـ`BEGIN;` وينتهي بـ`COMMIT;` — معاملة واحدة تحيط بالملف كله.
**والمعاملة لا تعبر بين لصقتين:** محرّر Supabase ينهي الجلسة بعد كل تنفيذ، فتبقى
معاملة معلّقة أو تُلغى بصمت.

فأضفنا `BEGIN` … `COMMIT` حول كل جزء. النتيجة:

| | الملف الأصلي | الأجزاء |
|---|---|---|
| البيانات النهائية | مطابقة | **مطابقة تماماً** |
| عند خطأ في المنتصف | يُلغى **كل** شيء | تبقى الأجزاء الناجحة، وتُكمل من موضع الخطأ |
| حاجة لإعادة من الصفر | دائماً | فقط الجزء الذي فشل |

هذا **أفضل** عملياً، وليس تنازلاً.

### وأيضاً: تعطيل المشغّلات

الملف الأصلي يعطّل المشغّلات بـ`SET LOCAL session_replication_role = replica`
ليُدخل البيانات التاريخية بلا تحقق. هذا `SET` ينتهي عند `COMMIT`. لذلك **كرّرناه
في كل جزء**. بدون هذا التكرار اشتغلت مشغّلات `audit_log` أثناء الإدخال فأضافت
صفوفاً وهمية — قِسناها: **١٤٦٦ صفاً بدل ١٢٤٠**. الآن مطابقة.

## التحقّق بعد الانتهاء

الصق هذا في استعلام جديد:

```sql
select 'jobs'           as الجدول, count(*) from brc.jobs
union all select 'applicants',    count(*) from brc.applicants
union all select 'job_attempts',  count(*) from brc.job_attempts
union all select 'audit_log',     count(*) from brc.audit_log
union all select 'issued_serials',count(*) from brc.issued_serials
union all select 'staff',         count(*) from brc.staff
order by 1;
```

وقارن بالأعداد المكتوبة أعلى ملف `2-data.sql` الأصلي (سطر «الأعداد»).
**يجب أن تتطابق حرفياً.**

وللتحقق من الهيكل:

```sql
select
  (select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'brc')            as دوال,
  (select count(*) from cron.job)      as مهام_مجدولة,
  (select count(*) from brc.settings)  as إعدادات;
```

المتوقع: **دوال ≥ ٦٣** · **مهام = ٤** · **إعدادات = ٢**.
لو `المهام = ٠` ← `pg_cron` غير مفعّلة (Database → Extensions).

## إن ظهر خطأ

**توقّف فوراً.** لا تلصق الجزء التالي — ستُضاعف المشكلة.

1. اقرأ أوّل سطر من الخطأ.
2. أرسله لي كما هو.
3. الجزء الفاشل وحده يُعاد لاحقاً؛ ما قبله مثبّت.

أخطاء شائعة:

| الخطأ | السبب | الحل |
|---|---|---|
| `relation "brc.X" does not exist` | تخطّيت جزءاً | أعِد الترتيب من حيث توقّفت |
| `canceling statement … timeout` | الجزء كبير أو القاعدة بطيئة | شغّله وحده، أو `alter database postgres set statement_timeout='5min';` |
| `extension "pg_cron" is not available` | غير مفعّلة | Database → Extensions → فعّلها ثم أعِد الجزء ١ |
| `duplicate key value` | شغّلت البيانات مرتين | الجزء ٦ يُفرّغ أولاً، فابدأ منه |

## توليد الأجزاء من جديد

لو تغيّر `docs/schema.sql` أو أعدت تصدير `2-data.sql`:

```bash
npm run sql:split                                   # السكيما
node tools/split-sql.mjs 2-data.sql --out docs/sql-parts/data
npm run sql:verify                                  # التحقق التنفيذي
```

الأداة تقطع **فقط** عند `;` خارج السلاسل النصية ودوال `$$…$$` والتعليقات، وتقسم
`INSERT` الضخمة على حدود الصفوف (لا داخل الصف)، وتغلق كل جزء بمعاملته.

> ⚠️ عند أي تعديل على `docs/schema.sql` شغّل `npm run schema:all` — يزامن ملف
> الـmigration **ويُحدّث المخطط المدمج في `restore.html`**. كان التحديث الثاني
> يدوياً فتقادم بصمت، فصار جزءاً من الأمر.

خيارات: `--lines 700` · `--bytes 180000` · `--quiet`.

## هل يظلّ صالحاً لو كبر المشروع؟ (سؤال المالك)

قسّنا عملياً بأحجام متزايدة — الأجزاء **لا تكبر**، عددها وحده يزيد:

| بطاقات | أسطر الملف | حجم | أجزاء | أكبر جزء | أكبر حجم |
|---|---|---|---|---|---|
| ٤٤٠ | ٣٥٦٠ | ٥١٣ ك.ب | ٨ | ٦٩٩ سطراً | ١٦٨ ك.ب |
| ١٠٠٠ | ٧٩٢٨ | ١١٤٨ ك.ب | ١٨ | ٦٩٩ سطراً | ١٧٧ ك.ب |
| ٣٠٠٠ | ٢٣٥٢٨ | ٣٤١٩ ك.ب | ٤٢ | ٦٩٩ سطراً | ١٧٧ ك.ب |
| **٦٠٠٠** | **٤٦٩٢٨** | **٦٨٣٨ ك.ب** | **٧٧** | **٦٩٩ سطراً** | **١٧٧ ك.ب** |

السقف ثابت مهما كبر الملف: **٦٩٩ سطراً / ١٧٧ ك.ب**. الذي يتغيّر هو عدد اللصقات.
٧٧ لصقة مزعجة لكنها آمنة؛ ومهلة الـ٦٠ ثانية لا تُلمس.

ونفّذنا ملف ٦٠٠٠ بطاقة فعلياً (٤٢١٢٨ سطراً، ١٢٠٠٠ محاولة، ١٢٠٠٠ تدقيق) على
قاعدة حقيقية: **٦٩ جزءاً، صفر إخفاقات، وكل الأعداد مطابقة**.

## ⚠️ فجوة كانت في النسخة نفسها — أُصلحت

سؤال «النسخة تتضمن كلشي؟» كشف عطلاً حقيقياً **أثبتناه تنفيذياً**، مستقلّاً عن
التقسيم: `recovery_export_v2` تصدّر **١٠ جداول** من ١٩ (و٢٢ بعد كل الهجرات).
فكان الاسترجاع على مشروع جديد يفقد بصمت:

| الجدول | ما الذي يُفقد | الأثر |
|---|---|---|
| `recovery_chances` | هل استُهلكت الفرصة | **البطاقة تمنح فرصتين؛ بعد الاسترجاع تصبح فرصاً غير محدودة** |
| `recovery_prints` | هل طُبعت البطاقة | إمكانية طباعة بطاقة ثانية برمز جديد |
| `office_receipts` | سجل عمليات المكتب | تكرار عملية بيع بدل ردّ النتيجة المحفوظة |
| `card_issue_requests` | طلبات الإصدار | فقدان أثر من طلب ماذا |
| `recovery_control.cutoff` | نقطة القطع الزمنية | النسخ التزايدي يبدأ من الصفر |

**الحل:** `supabase/migrations/20261115120000_portable_backup_v3.sql` —
دالة `recovery_export_v3()` تضيف هذه الخمسة فوق مخرَج v2، **ولا تصدّر السرّ**
(`recovery_control.secret` مستثنى صراحةً). وأُضيفت الجداول إلى
`assets/js/restore-sql.js` (ترتيب الإدخال + `TRUNCATE`) وإلا بقيت صفوف
المشروع القديم وتتعارض.

**ما لا يُصدَّر عمداً** (ذاكرة مؤقتة — نسخها يُقفل مستخدمين أبرياء على المشروع
الجديد، أو يضخّم النسخة بلا فائدة):

`card_security_attempts` · `card_lookup_budget` · `employer_login_budget` ·
`employer_otp` · `recovery_tickets` · `recovery_copies` (رموز استرجاع حيّة
ولقطات سابقة) · `jobs_image_url_rollback_20261112` (جدول تراجع منتهٍ).

**الإثبات:** اختبار ذهاب وعودة — بيانات في كل جدول ← تصدير ← استرجاع على
قاعدة فارغة ← مقارنة: **١٣ جدولاً، كل صف وصل، لا شيء فُقد**.

> ⚠️ الهجرة الجديدة تحتاج `supabase db push` (أو لصقها في SQL Editor).
> **تُطبَّق على قاعدة الإنتاج الحالية أيضاً**، لا على المشروع الجديد فقط —
> وإلا بقي التصدير ناقصاً حتى يوم الحاجة إليه.

## ما تحقّقنا منه فعلياً

لا نكتفي بفحص النص — نفّذنا الأجزاء على قاعدة PostgreSQL حقيقية (PGlite)،
**كل جزء بمعاملة منفصلة** كي نحاكي محرّر Supabase بالضبط:

```
── ① السكيما (٥ أجزاء) ──  ✅ ✅ ✅ ✅ ✅
── ② البيانات (٨ أجزاء) ──  ✅ ✅ ✅ ✅ ✅ ✅ ✅ ✅

jobs 47 · applicants 440 · job_attempts 880 · audit_log 1240
issued_serials 440 · staff 3 · settings 2 · card_number_registry 440
```

كلها مطابقة. الأجزاء الاثنا عشر مُنفَّذة، وفيها ١٣ فحصاً، صفر إخفاقات.

وأُعيد التحقق أيضاً بتصدير ٦٠٠٠ بطاقة: **٦٩ جزءاً، صفر إخفاقات**.

---

## حدّ الـ ٢٠٠٠ سطر

ذاك الرقم ليس حدّاً رسمياً في Supabase — لا حدّ أسطر موثّقاً. الجدار الحقيقي هو
**مهلة ٦٠ ثانية** للجملة الواحدة، وحدود المتصفّح في لصق نصّ ضخم. لذلك:
٧٠٠ سطر × ١٧٦ ك.ب لكل جزء حدّ آمن مريح، بعيد عن الجدارين.
